Well-Architected Framework AlignmentHow the labs map to the five WAF pillars — and what to change for production

Both labs are proof-of-concept environments. This page maps each lab's design choices against the Azure Well-Architected Framework pillars and highlights production-readiness gaps.

1. Reliability

AspectLab 1 — Easy AuthLab 2 — APIM
Redundancy Single Logic App instance, no redundancy in lab APIM Developer SKU — no SLA, single instance
Production recommendation Add multiple instances via App Service Plan scaling Use APIM Standard or Premium with availability zones
Health probes Default App Service health check Default App Service + APIM built-in health endpoint
Disaster recovery Not configured in lab Not configured in lab; APIM Premium supports multi-region

Production guidance: For Lab 1, add multiple Logic App instances behind load balancing. For Lab 2, upgrade from APIM Developer (no SLA) to Standard or Premium SKU with zone redundancy.

2. Security

AspectLab 1 — Easy AuthLab 2 — APIM
Identity enforcement Easy Auth + allowedPrincipals = identity at app level APIM validate-jwt + access restrictions = centralised + network
Defence-in-depth App-level auth + optional gateway Gateway auth + network isolation
HTTPS ✅ Enforced ✅ Enforced
Managed identities ✅ User-Assigned MI for APIM calling Logic App ✅ APIM has a system-assigned managed identity; current published policy evidence shows caller JWT validation, not backend managed-identity authentication
Shared keys SAS keys active alongside Entra (noted in threat model) Backend reachability is restricted; SAS disablement is not shown in the current evidence
Network controls No network isolation artifacts are shown in the current scan IP access restrictions on backend Logic App

Both labs: HTTPS is enforced. Managed identities are present in the resource inventory, but the currently published evidence should not be read as proof that every service-to-service hop is using managed identity authentication.

4. Operational Excellence

AspectLab 1 — Easy AuthLab 2 — APIM
Configuration model Per-app authsettingsV2 + SAS disable + env vars Centralised at APIM; simpler per-app config
Known gotchas Return401 breaks portal; platform.enabled + runtimeVersion underdocumented Fewer — standard APIM pattern
IaC ✅ Bicep ✅ Bicep
Monitoring Application Insights + Log Analytics Application Insights + Log Analytics + APIM analytics
Onboarding new apps Must replicate full authsettingsV2 config per app Add API + policy in APIM; backend uses standard access restrictions

Both labs use Infrastructure as Code (Bicep) and integrated monitoring (Application Insights). Lab 2 adds APIM built-in analytics for API-level visibility.

5. Performance Efficiency

AspectLab 1 — Easy AuthLab 2 — APIM
Call path Direct client-to-app — no gateway hop Client → APIM → Logic App (additional hop)
Latency Lower — no intermediary Slightly higher — APIM adds ~1–5 ms per call
Caching Not available at auth layer ✅ APIM response caching available
Throttling App-level only ✅ APIM rate-limiting and quota policies
Scaling App Service Plan auto-scale App Service Plan auto-scale + APIM capacity units

Trade-off: Lab 1 has lower latency for direct calls. Lab 2 adds a gateway hop but gains caching, throttling, and API-level governance — which typically outweigh the small latency increase in production scenarios.
