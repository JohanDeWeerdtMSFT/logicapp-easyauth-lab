Pillar 3: Service Endpoints + Storage FirewallSecure storage connectivity without Private Endpoint IP exhaustion

1. Overview

Logic App Standard requires a backing storage account for workflow state, run history, and artifact storage. Securing that storage link is essential — but every Private Endpoint consumes an IP address from your VNet.

The Problem Each storage account exposes four sub-resources (blob, queue, table, file). A Private Endpoint for each sub-resource means 4 IPs per storage account per app. At scale this exhausts subnet address space rapidly.
The Solution VNet Service Endpoints + storage firewall rules deliver subnet-level network isolation with 0 IPs consumed. Traffic stays on the Azure backbone, and the storage firewall restricts access to the authorized subnet only.

2. Private Endpoints vs Service Endpoints

Private Endpoint Approach

Logic App ──▶ VNet ──▶ PE NIC (10.0.1.5) ──▶ Storage (no public IP)
                       ↑ consumes 1 IP         ↑ private DNS zone needed
                       × 4 per storage (blob, queue, table, file)

Service Endpoint Approach

Logic App ──▶ VNet ──▶ Azure backbone ──▶ Storage (public FQDN, firewalled)
                       ↑ 0 IPs               ↑ firewall: allow subnet only
                       ↑ no DNS changes

Comparison

Private Endpoint Service Endpoint
IPs consumed 1 per PE (4 per storage acct) 0
DNS changes Private DNS zone + VNet link None
Storage has public IP? No (truly private) Yes (but firewalled to subnet)
Traffic path VNet → private IP in VNet Azure backbone (optimized route)

Setup complexity Higher (PE + DNS + NIC) Low (subnet toggle + firewall rule)
When to use Policy requires NO public IP Policy requires restricted access

Key Insight Managed connectors (Office 365, SharePoint) run in Microsoft's multitenant infrastructure outside your VNet. Service Endpoints and storage firewall rules do not affect those connectors — they only govern traffic from your VNet-integrated subnet to the storage account.

4. IP Consumption at Scale

The table below compares three approaches as the number of Logic Apps grows. Each app has one backing storage account with four sub-resources.

# Apps PE per app + PE per storage (4) APIM + PE per storage APIM + Service Endpoints
10 10 + 40 = 50 IPs 1 + 40 = 41 IPs 1 + 0 = 1 IP
50 50 + 200 = 250 IPs 1 + 200 = 201 IPs 1 + 0 = 1 IP
100 100 + 400 = 500 IPs 1 + 400 = 401 IPs 1 + 0 = 1 IP
200 200 + 800 = 1000 IPs 1 + 800 = 801 IPs 1 + 0 = 1 IP
Takeaway Service Endpoints eliminate storage-related IP consumption entirely. Combined with APIM for inbound, the total footprint stays at 1 IP regardless of fleet size.

6. Setup Steps

For each Logic App + storage account pair:

  1. Create a VNet (or use existing) with a subnet (/26 recommended).
  2. Add delegation Microsoft.Web/serverFarms to the subnet.
  3. Enable Service Endpoint for Microsoft.Storage on the subnet.
  4. VNet-integrate the Logic App (outbound traffic routes via the subnet).
  5. Set the storage account firewall: default action = Deny.
  6. Add a network rule: allow the Logic App subnet.
  7. Set bypass: AzureServices (for ARM management operations).
  8. Verify: Logic App can reach storage, external access is blocked.

7. Important Notes

Managed Connectors Are Not Affected Office 365, SharePoint, and other managed connectors run in Microsoft's multitenant infrastructure, outside your VNet. If an NSG or firewall blocks outbound traffic, you must allow the managed connector IP ranges separately.
Service Endpoints Require publicNetworkAccess: Enabled Service Endpoints use the storage account's public FQDN (firewalled to your subnet). If a tenant policy forces publicNetworkAccess: Disabled, you must use Private Endpoints instead.
One Subnet Serves Multiple Logic Apps All Logic Apps VNet-integrated into the same subnet share the service endpoint — no per-app setup needed for the endpoint itself. Only the storage firewall rule per storage account is app-specific.

8. When to Use Which

ScenarioRecommended Approach
Tenant policy: "No public IP on storage" Private Endpoints — accept the IP cost; no public surface at all
Tenant policy: "Restricted access from authorized networks" Service Endpoints — 0 IPs, subnet-restricted access
Mixed environment with different security zones Both approaches can coexist — use PEs for high-security zones, SEs elsewhere
