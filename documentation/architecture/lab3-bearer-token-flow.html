Lab 3 — Secure Service-to-Service Calls with Managed Identity Enable Function Apps and services to call Logic Apps without managing secrets or credentials

1. Overview

Lab 3 shows you how to build a production-ready architecture where a Function App securely calls a Logic App using bearer tokens. The critical innovation: your applications never store, rotate, or manage credentials. Instead, managed identity automatically handles authentication.

What This Solves: Enable service-to-service communication without SAS tokens, without shared secrets, and without manual credential rotation. Managed identity handles everything automatically.

This lab deploys to: Resource Group rg-la-easyauth-lab-dev

What You're Building

  • Function App Caller: Runs in a Standard S1 plan with system-assigned managed identity and VNet integration
  • Logic App Receiver: Runs in Standard WS1 plan, protected by Easy Auth and private endpoints
  • Authentication Method: OAuth 2.0 bearer tokens issued by Entra ID
  • Network Path: VNet integration + private DNS resolution + private endpoints
  • Authorization: Easy Auth with allowedPrincipals filter — only the Function App's identity is allowed

2. Three Core Components

A. Managed Identity (No Secrets)

The Function App has a system-assigned managed identity created automatically by Azure. This identity is used to acquire access tokens from Entra ID — no credentials are ever stored or managed by developers. 

// Bicep configuration (automatic)
identity: { type: 'SystemAssigned' }

// At runtime, the identity is available via the Azure Instance Metadata Service (IMDS)
// http://169.254.169.254/metadata/identity/oauth2/token

B. Bearer Token (Automatic Refresh)

When the Function App needs to call the Logic App, it requests an access token from Entra ID using its managed identity. The token is short-lived (1 hour) and automatically refreshed on each call via the DefaultAzureCredential library. 

// Token request
POST https://login.microsoftonline.com/{tenantId}/oauth2/v2.0/token
  scope: api://{logicAppEntraClientId}/.default
  client_id: {functionAppPrincipalId}

// Token response (JWT)
{
  "access_token": "eyJ0eXAiOiJKV1QiLCJhbGc...",
  "token_type": "Bearer",
  "expires_in": 3600
}

C. Easy Auth Validation (Zero Trust)

The Logic App's Easy Auth middleware validates every bearer token before allowing the request through. It checks:

  • Token signature (RS256, verified against Entra ID public keys)
  • Audience claim (must match Logic App's Entra app ID)
  • Token expiry (must not be expired)
  • Principal ID (must be in the allowedPrincipals list)

4. Step-by-Step Request Flow

Step 1: Function App Acquires Bearer Token

The Function App code uses DefaultAzureCredential from the Azure SDK to request an access token from the Entra ID Security Token Service (STS). The token is scoped to the Logic App's Entra application. 

// C# code running in Function App
var credential = new DefaultAzureCredential();
var logicAppEntraClientId = Environment.GetEnvironmentVariable("LOGIC_APP_AUDIENCE");

var tokenResponse = await credential.GetTokenAsync(
    new TokenRequestContext(new[] { $"{logicAppEntraClientId}/.default" })
);

var accessToken = tokenResponse.Token; // e.g., "eyJ0eXAiOiJKV1QiLCJhbGc..."

Step 2: Function App Sends HTTPS Request with Bearer Token

The Function App creates an HTTP request to the Logic App with the bearer token in the Authorization header. 

// HTTP request
POST https://la-easyauth-lab-dev-la-xxx.azurewebsites.net/api/httpTriggerWorkflow/triggers/manual/invoke?api-version=2022-05-01 HTTP/1.1
Authorization: Bearer eyJ0eXAiOiJKV1QiLCJhbGciOiJSUzI1NiJ9...
Content-Type: application/json
Host: la-easyauth-lab-dev-la-xxx.azurewebsites.net

{
  "requestBody": "sample data"
}

Step 3: DNS Resolution via Private DNS Zone

Because the Function App is VNet-integrated, its DNS queries are routed through the VNet's private DNS zone. The private DNS zone resolves *.azurewebsites.net to the private endpoint's IP address (10.0.1.x). 

// DNS resolution (in VNet)
Query: la-easyauth-lab-dev-la-xxx.azurewebsites.net
Response: 10.0.1.x (private endpoint IP)

// Without VNet integration, would resolve to:
Response: 20.y.z.w (public IP — blocked by public access disabled)

Step 4: Private Endpoint Routes to Logic App

The HTTPS request is routed to the private endpoint. The private endpoint accepts the connection and forwards it to the Logic App's Easy Auth middleware. Since publicNetworkAccess: Disabled, only traffic from the private endpoint is accepted.

Step 5: Easy Auth Validates Bearer Token

Easy Auth intercepts the request and validates the bearer token:

Validation Step Check Success Failure
1. Parse JWT Token format is valid JWT (3 base64 parts) Continue 401 Unauthorized
2. Verify Signature Token signed with Entra ID RS256 private key (verified against public key) Continue 401 Unauthorized
3. Check Audience (aud) Token's aud claim matches Logic App's Entra app ID Continue 401 Unauthorized
4. Check Expiry Token's exp claim is in the future Continue 401 Unauthorized
5. Extract Principal Extract appid or oid claim (the caller's identity) Continue 401 if claim missing
6. Check allowedPrincipals Principal is in the allowedPrincipals list ✅ Request allowed through 🔴 403 Forbidden

Step 6: Workflow Executes

Once Easy Auth validation passes, the request is routed to the Logic App runtime and the workflow executes normally. The response is returned to the Function App via the same private endpoint.

5. Bearer Token Anatomy (JWT Claims)

The access token returned from Entra ID is a JSON Web Token (JWT) containing the following important claims: 

{
  "header": {
    "alg": "RS256",
    "typ": "JWT",
    "kid": "key-id-for-signature-verification"
  },
  "payload": {
    "aud": "api://00000000-0000-0000-0000-000000000000",  // Logic App Entra app ID
    "appid": "11111111-1111-1111-1111-111111111111",      // Function App's MI principal ID
    "iat": 1688000000,                                     // Issued at (now)
    "exp": 1688003600,                                     // Expires (1 hour from now)
    "iss": "https://login.microsoftonline.com/22222222-2222-2222-2222-222222222222/v2.0",
    "oid": "11111111-1111-1111-1111-111111111111",        // Object ID (same as appid for managed identity)
    "scp": "",                                             // Scopes (empty, we use /.default)
    "sub": "11111111-1111-1111-1111-111111111111",        // Subject (caller's identity)
    "tid": "22222222-2222-2222-2222-222222222222",        // Tenant ID
    "unique_name": "la-easyauth-lab-dev-caller-daaq6t5xzrpaw"  // Managed identity display name
  },
  "signature": "S0mE_L0nG_bAsE64_EnCoDe..."
}

Key Claims for Validation:

  • aud — Audience. Must match Logic App's Entra app ID for the token to be valid for that app.
  • exp — Expiration time. Unix timestamp. Token is invalid if exp < current time.
  • appid or oid — Principal ID. Identifies the caller (Function App's managed identity).
  • iss — Issuer. Must be from Entra ID STS for the correct tenant.

6. Bearer Token vs SAS Token

Lab 3 uses bearer tokens instead of SAS tokens. Here's why:

Aspect SAS Token (❌ Lab 1 & 2) Bearer Token (✅ Lab 3)
Storage Location Stored in app settings or Key Vault
Must be managed by developers		 Acquired on-demand from Entra ID
Not stored in application state
Credential Rotation Manual rotation required
Risk of expiration in production		 Automatic (1-hour expiry)
No manual intervention needed
If Compromised Long-lived attack window
Attacker has access until key is rotated		 1-hour window only
Short-lived tokens limit damage
Scope / Permissions SAS tokens grant broad trigger permissions
Hard to granularly restrict		 Audience-scoped to single app
Easy Auth allowedPrincipals restricts further
Audit Trail Difficult to track who used the token
SAS token logs don't identify caller		 Entra ID logs show principal ID
Full audit trail of who called what
Multi-App Scalability Each app needs a unique SAS token
Scales linearly with number of apps		 One managed identity per app
Scales efficiently
Platform Integration No native support in Azure SDKs
Requires manual HTTP headers		 Native support via DefaultAzureCredential
Works with Azure SDK for any app

Token Acquisition (DefaultAzureCredential)

using Azure.Identity;
using Azure.Core;

// In your Function App code
public async Task<string> GetAccessTokenAsync()
{
    var credential = new DefaultAzureCredential(
        new DefaultAzureCredentialOptions { TenantId = Environment.GetEnvironmentVariable("WEBSITE_AUTH_AAD_ALLOWED_TENANTS") }
    );
    
    var audience = Environment.GetEnvironmentVariable("LOGIC_APP_AUDIENCE");
    var tokenResponse = await credential.GetTokenAsync(
        new TokenRequestContext(new[] { $"{audience}/.default" })
    );
    
    return tokenResponse.Token;
}

HTTP Request with Bearer Token

using System.Net.Http;
using System.Net.Http.Headers;

public async Task CallLogicAppAsync(string accessToken, object payload)
{
    var httpClient = new HttpClient();
    var logicAppUrl = Environment.GetEnvironmentVariable("LOGIC_APP_URL");
    
    // Add bearer token to Authorization header
    httpClient.DefaultRequestHeaders.Authorization = 
        new AuthenticationHeaderValue("Bearer", accessToken);
    
    // Serialize and send
    var content = new StringContent(
        JsonConvert.SerializeObject(payload),
        Encoding.UTF8,
        "application/json"
    );
    
    var response = await httpClient.PostAsync(logicAppUrl, content);
    response.EnsureSuccessStatusCode();
    
    var responseBody = await response.Content.ReadAsStringAsync();
    return responseBody;
}

Error Handling

try
{
    var token = await GetAccessTokenAsync();
    var result = await CallLogicAppAsync(token, new { message = "test" });
    _logger.LogInformation("Logic App call succeeded: {response}", result);
}
catch (HttpRequestException ex) when (ex.StatusCode == System.Net.HttpStatusCode.Unauthorized)
{
    _logger.LogError("401 Unauthorized — Token invalid (signature, audience, or expiry issue)");
    throw;
}
catch (HttpRequestException ex) when (ex.StatusCode == System.Net.HttpStatusCode.Forbidden)
{
    _logger.LogError("403 Forbidden — Principal ID not in allowedPrincipals list");
    throw;
}
catch (AuthenticationFailedException ex)
{
    _logger.LogError("Failed to acquire token — Managed Identity may not be enabled: {error}", ex.Message);
    throw;
}

10. Error Scenarios & Troubleshooting

❌ 401 Unauthorized — Invalid Token Signature

Cause: Token signed by wrong Entra tenant or tampered with

Check:

  • Verify LOGIC_APP_AUDIENCE environment variable is correct Entra app ID
  • Verify Function App's managed identity is in the same tenant as Logic App
  • Check Entra ID sign-in logs to see if token acquisition failed

❌ 401 Unauthorized — Audience Mismatch

Cause: Bearer token's aud claim doesn't match Logic App's Entra app ID

Check:

  • Decode token at jwt.ms and verify aud field
  • Ensure LOGIC_APP_AUDIENCE matches the Logic App's Entra app registration ID
  • If wrong audience, token was requested for a different app

❌ 403 Forbidden — Principal Not in allowedPrincipals

Cause: Bearer token is valid but caller (Function App's MI) is not in the allowedPrincipals filter

Check:

  • Verify Easy Auth allowedPrincipals includes Function App's managed identity principal ID
  • Check Azure portal: Logic App → Configuration → Authentication / Authorization → allowedPrincipals
  • Principal ID must match the Function App's system-assigned managed identity object ID

❌ 401 Unauthorized — Token Expired

Cause: Bearer token's exp claim is in the past

Check:

  • Tokens are short-lived (1 hour) — ensure DefaultAzureCredential is refreshing
  • Check function app logs for token acquisition errors
  • If clock skew suspected, sync time on Function App host (shouldn't happen in managed service)

⚠️ Network Error — Private Endpoint DNS Not Resolving

Cause: Private DNS zone not resolving *.azurewebsites.net to private endpoint IP

Check:

  • Verify Function App has VNet integration (Configuration → General → Virtual network integration)
  • Verify private DNS zone is linked to VNet
  • From Function App kudu console: nslookup la-easyauth-lab-dev-la-xxx.azurewebsites.net should return 10.0.1.x

❌ AuthenticationFailedException — Managed Identity Not Enabled

Cause: DefaultAzureCredential cannot acquire token (managed identity not configured)

Check:

  • Verify Function App has system-assigned managed identity (Identity → System assigned → Status: On)
  • Function App must be at least Standard (S1) plan to support VNet integration
  • If running locally (not in Azure), DefaultAzureCredential will fail — use VS Code Azure extension login as fallback

11. Bicep Configuration (Infrastructure as Code)

Function App with System-Assigned Managed Identity

resource functionApp 'Microsoft.Web/sites@2022-09-01' = {
  name: functionAppName
  location: location
  kind: 'functionapp'
  identity: {
    type: 'SystemAssigned'  // Automatic managed identity
  }
  properties: {
    serverFarmId: appServicePlan.id
    virtualNetworkSubnetId: vnetIntegrationSubnetId  // VNet integration
    vnetRouteAllEnabled: true  // Route all outbound through VNet
    httpsOnly: true
    appSettings: [
      { name: 'LOGIC_APP_URL', value: logicAppHttpTriggerUrl }
      { name: 'LOGIC_APP_AUDIENCE', value: 'api://${logicAppEntraClientId}' }
      { name: 'WEBSITE_AUTH_AAD_ALLOWED_TENANTS', value: entraAppTenantId }
    ]
  }
}

// Grant Storage access to managed identity
resource roleAssignment 'Microsoft.Authorization/roleAssignments@2022-04-01' = {
  scope: storageAccount
  name: guid(resourceGroup().id, functionApp.id, 'Storage Blob Data Contributor')
  properties: {
    principalId: functionApp.identity.principalId
    principalType: 'ServicePrincipal'
    roleDefinitionId: '/subscriptions/${subscription().subscriptionId}/providers/Microsoft.Authorization/roleDefinitions/ba92f5b4-2d11-453d-a403-e96b0029c9fe'
  }
}

Logic App with Easy Auth allowedPrincipals

resource easyAuthConfig 'Microsoft.Web/sites/config@2022-09-01' = {
  parent: logicApp
  name: 'authsettingsV2'
  properties: {
    platform: { enabled: true }
    globalValidation: {
      unauthenticatedClientAction: 'AllowAnonymous'  // Portal management works
      redirectToProvider: 'azureactivedirectory'
    }
    identityProviders: {
      azureActiveDirectory: {
        registration: { openIdIssuer: 'https://login.microsoftonline.com/${entraAppTenantId}/v2.0' }
        validation: {
          allowedAudiences: [ 'api://${logicAppEntraClientId}' ]
        }
      }
    }
    defaultAuthorizationPolicy: {
      allowedPrincipals: [
        { id: functionAppPrincipalId }  // Only Function App's MI can call
      ]
    }
  }
}

VNet with Private DNS Zone

resource privateDnsZone 'Microsoft.Network/privateDnsZones@2020-06-01' = {
  name: 'privatelink.azurewebsites.net'
  location: 'global'
}

resource privateDnsZoneLink 'Microsoft.Network/privateDnsZones/virtualNetworkLinks@2020-06-01' = {
  parent: privateDnsZone
  name: '${vnet.name}-link'
  location: 'global'
  properties: {
    registrationEnabled: false
    virtualNetwork: { id: vnet.id }
  }
}

resource privateEndpoint 'Microsoft.Network/privateEndpoints@2022-09-01' = {
  name: 'pe-logic-app'
  location: location
  properties: {
    subnet: { id: privateEndpointSubnetId }
    privateLinkServiceConnections: [
      {
        name: 'logic-app-connection'
        properties: {
          privateLinkServiceId: logicApp.id
          groupIds: [ 'sites' ]
        }
      }
    ]
  }
}

// DNS group links private endpoint to private DNS zone
resource dnsGroup 'Microsoft.Network/privateEndpoints/privateDnsZoneGroups@2022-09-01' = {
  parent: privateEndpoint
  name: 'default'
  properties: {
    privateDnsZoneConfigs: [
      {
        name: 'config'
        properties: {
          privateDnsZoneId: privateDnsZone.id
        }
      }
    ]
  }
}

13. When to Use Lab 3 Pattern

The Lab 3 pattern is ideal for:

  • Self-contained workloads: Function App and Logic App are part of the same solution (not multi-tenant API)
  • Secure by default: Want identity-based auth without APIM complexity
  • Few callers: Only a handful of apps need access (use allowedPrincipals for each)
  • Temporary integrations: Ephemeral service-to-service calls, not a stable public API
  • Internal teams: Both caller and receiver are within the same organization

Not recommended for:

  • Public APIs with many external callers (use API Management instead)
  • Legacy systems without Azure SDK support (DefaultAzureCredential not available)
  • Cross-organizational integrations (partner access — use APIM + allowlists)
