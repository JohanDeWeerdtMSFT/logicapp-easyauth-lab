Decision GuidanceCustomer-Facing Comparison — Easy Auth vs APIM-Centric Security

Use Request & Data Flow alongside this page when you need to explain exactly where authentication, authorization, and access restrictions are applied.

1. Purpose

This repository contains two complementary security labs for Azure Logic App Standard. They exist because no single pattern optimises for every customer constraint at once.

The goal of this page is to:

  • Explain why two labs exist side by side
  • Present a clear, honest comparison of trade-offs
  • Help customers (and field engineers) make an informed architecture decision rather than a forced one

2. Side-by-Side Comparison

4. Option A vs Option B for Lab 1

Lab 1 can be configured in two ways. Only Option A has been fully validated.

Aspect Option A — AllowAnonymous + allowedPrincipals Option B — Return401 + excludedPaths
Validation status Validated ✅ Documented — not yet tested
Portal management ✅ Works — unauthenticated management requests pass through ✅ Expected to work — excluded paths bypass Easy Auth
Token enforcement ✅ Requests with Authorization header validated ✅ Stricter — all requests to non-excluded paths require Entra token
SAS keys Active — can trigger workflows without Entra token Blocked for non-excluded paths
Strictness Medium — unauthenticated requests without tokens reach runtime High — but excluded paths lose Easy Auth protection
Trade-off SAS bypass possible; simpler config Excluded paths unprotected; glob patterns need testing

5. Why Some References Combine APIM + Easy Auth

Several external references intentionally use both APIM and Easy Auth to achieve:

  • Maximum identity strictness at every layer
  • Explicit prevention of backend bypass
  • Strong defence-in-depth

However, this comes with:

  • Increased configuration complexity
  • Higher operational risk for Logic Apps Standard (Easy Auth gotchas)
  • Greater sensitivity to platform changes

Those references are not wrong — they simply optimise for a different set of constraints. If your customer requires identity enforcement at both gateway and app host, the combined approach is valid — but deploy it consciously, not accidentally.

6. How to Use Both Labs with a Customer

  1. Walk through both labs conceptually — explain what each optimises for and what it trades off.
  2. Ask which constraints matter most: Identity strictness vs operational simplicity? Small number of apps vs hundreds? IP address availability a concern? Portal manageability critical?
  3. Present the comparison table (Section 2) and let the customer see the trade-offs side by side.
  4. Use the decision flowchart (Section 3) as a conversation starter, not a prescription.
  5. Decide together whether:
    • Lab 1 fits best (few apps, maximum identity strictness)
    • Lab 2 fits best (many apps, centralised governance)
    • Or elements of both are required — consciously and carefully
  6. Document the decision — capture which pattern was chosen and why, so it can be revisited as requirements evolve.

The labs are conversation tools, not prescriptions. Use them to guide discussion, not to force a conclusion.

7. Key Message

There is no single "best" pattern. The right design is the one that aligns with the customer's risk tolerance, scale, and operational model.
