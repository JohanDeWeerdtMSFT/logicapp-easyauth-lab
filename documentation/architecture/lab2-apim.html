Lab 2 — APIM-Centric Security Centralized JWT validation at API Management, no Easy Auth on Logic App

1. Overview

This lab demonstrates centralized Entra ID JWT validation at Azure API Management, with backend Logic Apps protected via network-level access restrictions instead of Easy Auth. The Logic App has no authsettingsV2 configured.

Resource Group: rg-la-easyauth-lab-apim-dev

  • Track C — APIM JWT validation (valid / invalid / missing token)
  • Track D — Backend isolation (Logic App unreachable directly)
  • Track E — Portal manageability (no Easy Auth interference)

For the shared explanation of where APIM authentication ends and backend access restrictions begin, see Request & Data Flow.

API Management validates the Entra ID JWT before forwarding to the Logic App backend. Access restrictions on the Logic App ensure only APIM traffic is accepted. The Logic App has no Easy Auth configured — portal and management access is fully preserved.

3. APIM JWT Validation Policy

This validate-jwt inbound policy validates Entra ID v2.0 tokens at the APIM layer before any request reaches the Logic App backend: 

<policies>
    <inbound>
        <base />

        <!-- Validate JWT from Entra ID -->
        <validate-jwt
            header-name="Authorization"
            failed-validation-httpcode="401"
            failed-validation-error-message="Unauthorized. A valid Entra ID bearer token is required."
            require-expiration-time="true"
            require-scheme="Bearer"
            require-signed-tokens="true"
            output-token-variable-name="jwt">

            <!-- Entra ID v2.0 OpenID Connect metadata -->
            <openid-config
                url="https://login.microsoftonline.com/{{tenant-id}}/v2.0/.well-known/openid-configuration" />

            <!-- Audience must match the app registration -->
            <audiences>
                <audience>{{client-id}}</audience>
            </audiences>

            <!-- Issuer must be the correct Entra tenant -->
            <issuers>
                <issuer>https://login.microsoftonline.com/{{tenant-id}}/v2.0</issuer>
                <issuer>https://sts.windows.net/{{tenant-id}}/</issuer>
            </issuers>

        </validate-jwt>

        <!-- Forward caller identity to backend -->
        <set-header name="X-Authenticated-User" exists-action="override">
            <value>@(context.Request.Headers.GetValueOrDefault("Authorization","").AsJwt()?.Subject)</value>
        </set-header>

    </inbound>

    <backend>
        <base />
    </backend>

    <outbound>
        <base />
    </outbound>

    <on-error>
        <base />
    </on-error>
</policies>

5. Clarification: Why Not Both APIM + Easy Auth?

Some references combine API Management and Easy Auth for defense-in-depth identity enforcement. While valid, enabling Easy Auth on Logic Apps Standard can introduce operational complexity and runtime manageability risks. This lab demonstrates an alternative pattern where API Management enforces identity centrally, and backend Logic Apps are protected using network-level access restrictions. The current deployment evidence does not show VNet or Private Endpoint resources.

9. IP Address Scalability

A key architectural advantage of the APIM-centric pattern is that one gateway can front multiple backend apps. The current deployment evidence does not show Private Endpoints, so the table below should be read as production design guidance rather than a statement about this specific lab deployment.

# of Apps Easy Auth (PE per app) APIM Centralized
10 10 IPs 1 APIM IP
50 50 IPs 1 APIM IP
200 200 IPs 1 APIM IP

For customers operating hundreds of Logic Apps and Function Apps, the APIM-centric pattern can simplify governance and reduce repeated per-app ingress configuration.

flowchart LR C["Client"] APIM["APIM - JWT Validation"] LA["Logic App (access restricted)"] Sub["snet-logicapp 10.20.1.0/26"] SE["Service Endpoint"] ST["Storage (firewalled)"] C -- "Bearer token" --> APIM APIM -- "51.145.176.4 allowed" --> LA LA -- "VNet integration" --> Sub Sub --> SE SE -- "Allowed by firewall" --> ST

The complete flow: the client presents an Entra ID bearer token to APIM, which validates the JWT. APIM forwards the request to the Logic App, which only accepts traffic from the APIM IP and AzureCloud. The Logic App reaches its storage account through VNet integration and a Service Endpoint — the storage firewall denies all traffic except from the delegated subnet.
