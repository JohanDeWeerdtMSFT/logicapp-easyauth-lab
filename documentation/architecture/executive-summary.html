Executive Summary Three Security Pillars for Logic App Standard

Last updated: 2026-04-08

Recommended Walkthrough Order Start with Request & Data Flow for the layer-by-layer explanation, then use this page for the three-pillar summary and the lab pages for configuration detail.

Core Finding

Securing Logic App Standard at enterprise scale requires three complementary pillars, each addressing a distinct attack surface. No single pillar is sufficient on its own — together they provide identity enforcement, centralized API governance, and network isolation without IP exhaustion.

Pillar 1 — Easy Auth (Identity at the App Level)

1 What

Enable Easy Auth (authsettingsV2) on every Logic App and Function App with AllowAnonymous + allowedPrincipals.

Why It Works

AllowAnonymous lets portal and management-plane calls through — they don't carry app-level tokens. Requests with a bearer token are still strictly validated against Entra ID (audience, principal, tenant). Using Return401 instead breaks the portal — this is confirmed by Microsoft Learn.

Setup Steps per App

  1. Create a blank Entra ID App Registration (no secrets, no redirect URIs needed)
  2. Configure authsettingsV2: AllowAnonymous, platform.enabled: true, runtimeVersion: ~1
  3. Set allowedAudiences to management-plane audiences
  4. Set allowedPrincipals.identities to the calling identity (e.g., APIM managed identity)
  5. Add WEBSITE_AUTH_AAD_ALLOWED_TENANTS app setting with tenant ID
  6. Store client secret via MICROSOFT_PROVIDER_AUTHENTICATION_SECRET (Key Vault reference)

✅ Track A — Portal works ✅ Track B — Tokens enforced

Pillar 2 — APIM (Centralized Inbound Auth Gateway)

2 What

Place Azure API Management in front of Logic Apps to centralize JWT validation instead of configuring Easy Auth per-app.

Why APIM

  • Centralizes auth config — 1 place instead of N apps
  • validate-jwt policy validates caller tokens before reaching the backend
  • Reduces need for per-app Private Endpoints for inbound traffic (access restrictions on Logic Apps allow only APIM)
  • Provides rate limiting, logging, transformation, and API governance
  • Does not replace Easy Auth — it is an alternative for inbound auth at scale
⚠️ Managed Connectors Are Not Affected Office 365, SharePoint, file connector, and other managed connectors are shared/hosted by Microsoft in multitenant Azure. They run outside your VNet. Outbound calls from your Logic App to these connectors go through the managed connector infrastructure, not through your VNet or APIM. VNet integration affects only outbound traffic from built-in connectors. If your VNet has an NSG or firewall, you must allow outbound traffic to the managed connector IP addresses for your region.

Setup Steps

  1. Deploy APIM (Developer tier for lab, Standard/Premium for production)
  2. Enable system-assigned managed identity on APIM
  3. Create validate-jwt inbound policy with tenant/audience/issuer config
  4. Create backend pointing to Logic App hostname
  5. Add access restrictions on each Logic App: allow only APIM IP, deny all others
  6. For Easy Auth pattern: use authentication-managed-identity policy so APIM gets its own bearer token

✅ Track C — JWT validation ✅ Track D — Backend isolation ✅ Track E — Portal works

Pillar 3 — Service Endpoints + Storage Firewall (Network Isolation)

3 What

Use VNet Service Endpoints instead of Private Endpoints for storage account connectivity.

Why

Each Logic App needs a storage account. With Private Endpoints, that's 4 PEs per storage (blob, queue, table, file) = 4 IPs per app. At 100 apps that's 400 IPs just for storage. Service Endpoints use 0 IPs.

How It Works

  • Enable Service Endpoint for Microsoft.Storage on the Logic App subnet
  • VNet-integrate the Logic App (outbound traffic routes through VNet)
  • Set storage firewall: default action = Deny, allow the Logic App subnet
  • Traffic goes over Azure backbone (never public internet)
  • Storage keeps its public FQDN but firewall restricts to authorized subnets only

Private Endpoints vs Service Endpoints

Private Endpoint Service Endpoint
IPs consumed 1 per PE (4 per storage) 0
DNS changes Private DNS zone required None
Storage public IP Removed (truly private) Kept (but firewalled)
Traffic path VNet → private IP Azure backbone (optimized)
Cost ~€7/mo per PE Free
Security level Strongest (no public surface) Strong (subnet-restricted)
Setup complexity Higher (PE + DNS + NIC) Low (subnet toggle + firewall)
When to use Private Endpoints: Policy requires storage has NO public IP at all.
When to use Service Endpoints: Policy requires storage only reachable from authorized networks.

✅ Both labs — VNet + Service Endpoints + storage firewalled

Architecture — Three Pillars Combined

A recommended hub-spoke topology with security controls: centralized firewall (Pillar 3), APIM gateway (Pillar 2), Easy Auth on Logic Apps (Pillar 1), and private endpoints for storage. The diagram below is interactive — hover over nodes for details, and drag to reposition.

What You're Seeing
  • Hub VNet: Contains Azure Firewall for centralized traffic inspection and routing
  • Spoke 1 & 2: Isolated application subnets with Logic Apps, backed by private storage accounts
  • Private Endpoints: Secure storage connectivity without consuming extra IPs (Pillar 3)
  • APIM: Centralized inbound auth gateway with validate-jwt policy (Pillar 2)
  • NSGs: Network security groups restrict inbound to authorized sources only (Pillar 1 + 2)
  • Colour legend: Blue = API calls, Green = Data, Orange = Security, Purple = Network/Private

IP Consumption at Scale

The table below shows how IP address consumption grows with each deployment pattern. Pillar 3 (Service Endpoints) eliminates IP exhaustion entirely.

Scenario 10 apps 50 apps 200 apps
PE per app + PE per storage (4 each) 50 IPs 250 IPs 1,000 IPs
