Lab 1 — Easy Auth (AllowAnonymous Pattern) Validate Easy Auth on Logic App Standard without breaking portal manageability

1. Overview

This lab validates that Azure App Service Easy Auth (authsettingsV2) can secure Logic App Standard HTTP triggers using the AllowAnonymous + allowedPrincipals pattern — without breaking portal manageability or ARM management operations.

Resource Group: rg-la-easyauth-lab-dev

  • Track A — Portal manageability (Return401 vs AllowAnonymous)
  • Track B — Trigger security (Entra token enforcement despite AllowAnonymous)

For the cross-lab explanation of where requests are authenticated, authorized, and blocked, see Request & Data Flow.

Easy Auth intercepts requests that carry an Authorization header and validates them against the configured Entra ID requirements. Requests without an Authorization header (such as portal/ARM management calls and SAS-authenticated triggers) pass through under the AllowAnonymous setting.

3. Easy Auth Configuration

The authsettingsV2 resource is configured as follows:

{
  "properties": {
    "platform": {
      "enabled": true,
      "runtimeVersion": "~1"
    },
    "globalValidation": {
      "unauthenticatedClientAction": "AllowAnonymous",
      "redirectToProvider": "azureactivedirectory"
    },
    "identityProviders": {
      "azureActiveDirectory": {
        "enabled": true,
        "registration": {
          "clientId": "<entra-app-client-id>",
          "openIdIssuer": "https://sts.windows.net/<tenant-id>/v2.0",
          "clientSecretSettingName": "MICROSOFT_PROVIDER_AUTHENTICATION_SECRET"
        },
        "validation": {
          "allowedAudiences": [
            "https://management.azure.com"
          ],
          "defaultAuthorizationPolicy": {
            "allowedPrincipals": {
              "identities": [
                "<apim-managed-identity-object-id>"
              ]
            }
          }
        }
      }
    }
  }
}

Required environment variable on the Logic App:

WEBSITE_AUTH_AAD_ALLOWED_TENANTS = "<tenant-id>"

Key settings:

  • platform.enabled: true and runtimeVersion: ~1 are mandatory but underdocumented
  • unauthenticatedClientAction: AllowAnonymous preserves portal access
  • allowedAudiences restricts accepted token audiences
  • allowedPrincipals.identities limits access to the APIM managed identity

4. Why AllowAnonymous (Not Return401)

The initial lab testing with Return401 confirmed that Easy Auth blocks all /hostruntime/* data-plane endpoints, breaking portal manageability for scenarios A1–A4.

“If unauthenticatedClientAction is set to Return401, the request doesn't get routed to the Azure Logic Apps runtime and fails with 401 from App Service. With this error, you also get a broken Azure portal experience.”

— Microsoft Learn — Method 2: Easy Auth

With AllowAnonymous, requests that include an Authorization header are still validated by Easy Auth. Requests without a token (portal management, ARM calls, SAS triggers) pass through to the Logic App runtime. This preserves both security and operability.

8. Alternative: excludedPaths

An alternative approach keeps Return401 for maximum strictness but exempts management endpoints via excludedPaths: 

{
  "globalValidation": {
    "unauthenticatedClientAction": "Return401",
    "excludedPaths": [
      "/runtime/*",
      "/hostruntime/*"
    ]
  }
}

Status: Not yet validated in this lab. This is a documented alternative that may achieve stricter enforcement while preserving portal access, but requires testing to confirm glob pattern support and which paths need excluding.

Conclusion: How Easy Auth Works with AllowAnonymous

The key insight is one setting and how Easy Auth treats requests differently based on whether they carry a token or not.

Portal / Management Calls (No App-Level Token)

You (portal) → Azure ARM → Logic App hostruntime
                            │
                            │  This request has your ARM token,
                            │  but NOT an app-level bearer token
                            │  in the format Easy Auth expects
                            │
                            ▼
                      Easy Auth middleware
                            │
                  "Is there an Authorization header
                   with a bearer token for MY app?"
                            │
                           NO
                            │
              ┌─────────────┴──────────────┐
              │                            │
         Return401 mode            AllowAnonymous mode
              │                            │
         ❌ BLOCKED                   ✅ PASS THROUGH
         "401 Unauthorized"         Let the runtime handle it
                                    (ARM already authenticated you)

APIM Calls with Valid Entra Token

APIM → Logic App trigger endpoint
        │
        │  Authorization: Bearer <Entra token>
        │
        ▼
  Easy Auth middleware
        │
  "Is there a bearer token?" → YES
        │
  "Valid Entra token?"       → YES
  "Right audience?"          → YES
  "Right principal (APIM MI)?" → YES
        │
        ✅ ALLOWED

Attacker Calls with Bad Token

Attacker → Logic App trigger endpoint
            │
            │  Authorization: Bearer <bad-token>
            │
            ▼
      Easy Auth middleware
            │
      "Is there a bearer token?" → YES
      "Valid Entra token?"       → NO
            │
            ❌ 401 REJECTED

The Key Insight

AllowAnonymous does not mean "no security" — it means:

  • No token? → pass through to runtime (runtime still needs SAS key or ARM auth)
  • Has token? → validate it strictly (audience, principal, tenant)

The portal’s management calls fall into the “no token” category — they are authenticated by ARM, not by an app-level bearer token. Return401 doesn’t understand this distinction and blocks everything. AllowAnonymous lets them through.

Summary

CallerHas App Token?Return401AllowAnonymous
Azure Portal (run history, details) No ❌ 401 Blocked ✅ Pass through
APIM with valid MI token Yes (valid) ✅ Allowed ✅ Allowed
Attacker with invalid token Yes (invalid) ❌ 401 ❌ 401
Attacker with wrong principal Yes (wrong identity) ❌ 403 ❌ 403
Request with SAS key only No ❌ 401 Blocked ✅ SAS accepted by runtime
No auth at all No ❌ 401 ❌ 401 (no SAS = rejected by runtime)
