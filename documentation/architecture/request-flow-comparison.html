Request and Data Flow Comparison

A customer-facing explanation of where routing, authentication, authorization, and access control happen in each lab

Diagram Source Artifact A draw.io source version of this comparison is available at architecture/diagrams/request-auth-dataflow-comparison.drawio for editing or export in the draw.io VS Code extension. Interactive HTML diagrams with official Azure icons: Lab 1 — Easy Auth · Lab 2 — APIM-Centric.

Why This Page Exists

The two labs secure the same Logic App Standard trigger in different places. The critical design difference is not only which Azure service validates the caller, but also which requests reach the Logic App host, which requests touch the workflow runtime, and which requests are blocked before they ever reach application code.

Evidence Scope This comparison is grounded in the scan artifacts under documentation/azure-scan and the validated findings in the evidence section. Where the current deployment evidence does not show a control, the page states that explicitly.

Layer Comparison

Layer Lab 1 — Easy Auth on Logic App Lab 2 — APIM in Front
Ingress path Caller reaches the Logic App endpoint directly Caller reaches APIM first; APIM forwards allowed requests to the Logic App backend
Authentication Easy Auth validates requests that include an Authorization header APIM validate-jwt validates caller tokens on inbound requests
Authorization allowedPrincipals restricts which identities are allowed after token validation Current evidence shows JWT validation at APIM; backend identity authorization beyond network access is not shown in the published policy
No-token behavior Requests without an Authorization header pass to the runtime under AllowAnonymous; runtime behavior then decides outcome, including SAS-based success Requests without a token are rejected by APIM before they reach the backend
Network control No VNet or Private Endpoint artifacts are present in the current scan Backend access restrictions are the demonstrated isolation control
Portal manageability Validated only when Easy Auth is configured to allow hostruntime requests through, such as the current AllowAnonymous mode Validated because Easy Auth is disabled on the backend app

Request Boundaries

flowchart LR caller["External caller"] --> direct["Direct request path"] portal["Azure portal or ARM"] --> arm["ARM control plane"] arm --> hostruntime["hostruntime management operations"] direct --> gateway["APIM gateway in Lab 2"] direct --> host["Logic App host in Lab 1"] gateway --> host host --> easyauth["Easy Auth middleware when enabled"] easyauth --> runtime["Workflow runtime"] hostruntime --> host

The most important boundary is between ARM operations that stay in the ARM provider and requests that are proxied into the Logic App host through hostruntime. In Lab 1, Easy Auth can intercept those host-bound requests. In Lab 2, the backend app has Easy Auth disabled, so those hostruntime operations remain accessible in the current evidence.

Lab 1 — Easy Auth Request Flow

flowchart TD mgmt["Portal or ARM hostruntime request"] --> noheader["No app bearer token at Easy Auth boundary"] noheader --> mode{"Easy Auth mode"} mode -->|"AllowAnonymous"| runtimeMgmt["Request reaches workflow runtime"] runtimeMgmt --> portalOk["Validated run history and callback URL stay accessible"] mode -->|"Return401"| blockedMgmt["Easy Auth returns 401 before runtime"] tokenCaller["Caller with Authorization header"] --> validate["Easy Auth validates audience and principal"] validate -->|"Invalid token or wrong audience"| reject401["401"] validate -->|"Valid token but identity not allowed"| reject403["403"] validate -->|"Allowed token"| runtimeToken["Workflow runtime"] noTokenCaller["Caller without Authorization header"] --> runtimeDecision["Runtime decides outcome"] runtimeDecision -->|"SAS present"| sas200["200"] runtimeDecision -->|"No SAS"| noSas401["401"]
Key Lab 1 Point AllowAnonymous does not mean the trigger is universally open. It means Easy Auth only evaluates requests that actually carry an Authorization header. Requests without one continue to the runtime, where SAS or runtime validation determines the result.

Lab 2 — APIM Fronted Request Flow

flowchart TD apimCaller["Caller with bearer token"] --> jwt["APIM validate-jwt policy"] jwt -->|"Invalid or missing token"| apim401["401 at APIM"] jwt -->|"Valid token"| forward["APIM forwards request and sets X-Authenticated-User"] forward --> backend["Logic App backend"] backend --> runtime2["Workflow runtime because Easy Auth is disabled"] directCaller["Direct caller bypassing APIM"] --> access["Backend access restrictions"] access --> directBlocked["Blocked in current evidence: 401"] portal2["Portal or ARM hostruntime request"] --> backend backend --> portal2ok["Validated hostruntime operations stay accessible"]
Key Lab 2 Point APIM handles caller authentication. The backend Logic App is protected by access restrictions and does not run Easy Auth in the current deployment. That is why portal manageability remains available while direct bypass calls are still blocked.

Terminology

Term Meaning In These Labs
Authentication Checking whether the caller presents a valid token from the expected issuer and audience
Authorization Checking whether an authenticated identity is allowed to proceed, such as allowedPrincipals in Lab 1
Access restriction Network-layer allow or deny behavior at the app boundary, independent of token validation
Portal manageability The ability to use run history, run details, inputs and outputs, and callback URL operations through Azure management experiences
hostruntime Management operations proxied into the Logic App host rather than handled entirely within ARM
SAS A runtime-level shared access signature capability that can still authorize a trigger even when no bearer token is present
